# 0025. 機器マスタは分類ごとの Firestore の文書で編集し、同期で公開する

- 状態: 採用
- 日付: 2026-09-25
- 関連: [0018](0018-撮影機器を分類から始まる4段にする.md)、[0013](0013-同期より後の変更はupdatedAtで表す.md)、T28

## 背景

機器マスタ（ADR 0018）の元データは `scripts/data/equipment-master.mjs` にあり、機器を足すにはコードの変更と公開が要った。
管理者が画面で足し引きできるようにしたい。一方で、分類のキーは src・ルール（`validEquipment`）・マスタの 3 か所にあり、
画面で分類を増やすとルールが新しい分類のマーカーを拒否する。

## 決定

1. **分類（9 つ）はコードに残す。** 画面で編集できるのは、分類の中のメーカー・シリーズ・モデルだけ。
   分類を足すのは今までどおりコードの変更（`src/core/constants/equipment.ts`、ルールの `validEquipment`（`rules/10-markers.rules`）と `validEquipmentMaster`（`rules/38-equipment.rules`）、`scripts/data/equipment-master.mjs`、同期の `scripts/lib/equipment-master.mjs` の `CATEGORIES` の 5 か所。`npm run verify` が一致を検査する）。
2. 編集した分類は `equipmentMaster/{分類のキー}` に 1 文書で置く（`makers`・`updatedAt`）。
   読むのは誰でも（同期は API キーだけで読む）。誰が直したか（管理者の uid）は置かない（`admins` を伏せているため）。書く・消すのは管理者だけ。入れ子の中身（名前の長さ・重複・件数）はルールでは検査しきれないので、
   ルールは形とメーカーの件数だけを守り、中身は画面と同期の両方で検査する（1 分類でメーカー 60・シリーズ 200・モデル 1000 まで）。
3. **公開は同期（`scripts/sync-firestore.mjs`）が `public/data/equipment.json` を作り直して行う。**
   分類ごとに「Firestore の文書があればそれ、無ければ `equipment-master.mjs`」を使う。検査に落ちた文書は使わず、同期の結果に NG として出す。
   フォームは今までどおり `equipment.json` だけを読む。購読（ADR 0013）はしないので、反映は次の同期（毎晩、または同期の手動実行）。
4. 文書を消すと、その分類はコードの既定に戻る（画面の「既定に戻す」）。
5. 画面の入力は字下げの文章にする（メーカー → 2 字下げでシリーズ → 4 字下げでモデル）。4 段の入れ子の一覧を作るより部品が小さく、
   貼り付けでまとめて直せる。文章と一覧の変換と検査は `src/core/logic/equipmentText.ts`。

## 検討した代替案

- **分類も画面で編集する**: ルールの `validEquipment` を Firestore の値で判定すると、マーカーの書き込みごとに get が増える（バッチあたり 20 回の上限）。却下。
- **マスタ全体を 1 文書に置く**: 1 分類を直すだけで全体を書き換え、同時に直すと後勝ちで消える。却下。
- **フォームが Firestore を直接読む**: 初期表示の読み取りが利用者の数だけ増え、Spark の無料枠を食う。却下。

## 結果

- モデルを消しても、それを付けた既存のマーカーはそのまま表示される。ただしそのマーカーを編集するときは、機器を選び直す必要がある
  （`isValidEquipment` がマスタに無い組み合わせを拒む）。
- `equipmentMaster` は試験データではないので、`reset-data` では残す（`KEEP`）。

## 確かめ方

管理者モードの「機器」で分類を選び、モデルを 1 つ足して保存する。同期を手動で実行したあと、投稿フォームの機器の選択肢にそのモデルが出る。
