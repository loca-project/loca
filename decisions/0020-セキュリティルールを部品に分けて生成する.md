# 0020. セキュリティルールを部品に分けて書き、firestore.rules は生成する

- 状態: 採用
- 日付: 2026-09-24
- 関連: [0012](0012-Firestoreのデータ形とルールの方式.md)

## 背景

プロフィール（ADR 0019）のルールを足すと、`firestore.rules` が 425 行になり、コードの上限（CP-2。400 行）を超えた。
Firestore のルールは 1 ファイルしか反映できず、ほかのファイルを読み込む構文も無い。

## 決定

1. ルールは `rules/*.rules` に、コレクションのまとまりごとに分けて書く（共通・マーカー・撮影リクエスト・回答・通報・いいね・機器マスタ・利用者）。
2. `npm run rules:build`（`scripts/build-rules.mjs`）が名前順につなぎ、`firestore.rules` を作る。**`firestore.rules` は手で編集しない。**
3. `firestore.rules` はリポジトリに残す。反映（`firebase deploy`）・テスト・`release.mjs` の差分判定は今までどおりこのファイルを見る。
4. `npm run test:rules` は先に `rules:build` を走らせる。`npm run verify` は `firestore.rules` が部品と一致することを検査する。

## 検討した代替案

- **1 ファイルのまま行を詰める**: 上限を避けるための小細工になる（Core ポリシー「違反したとき」）。却下。
- **生成物をリポジトリに置かない**: `firebase deploy` と `release.mjs` の手前で必ず生成する必要があり、忘れると古いルールが出る。却下。

## 結果

- 最初の部品が `service` と `match` を開き、最後の部品が閉じる。部品を足すときは名前の順番に気をつける。
- 部品を変えて `rules:build` を忘れると、`npm run check`（verify）が落ちる。

## 確かめ方

`node scripts/build-rules.mjs --check` と、`npm run verify` の「firestore.rules が rules/ の部品と一致」が OK。
