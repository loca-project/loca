# 0012. Firestore のデータ形とセキュリティルールの方式

- 状態: 採用
- 日付: 2026-09-24
- 関連: [0010](0010-書き込みと認証にFirebase無料プランを使う.md)

## 背景

0010 で「権限はすべてセキュリティルールで守る」と決めた。
ルールを書くには、コレクションの形と、レートリミットの実現方法を先に決める必要がある。
Spark では Cloud Functions が使えないので、サーバー側の検査はルールだけで完結させる。

## 決定

1. **ルールの対象はマーカー・管理者・ブラックリスト・レートリミットの 4 コレクション**にする。
   それ以外（いいね・通報・撮影リクエスト・プロフィール）は、実装するときにルールとテストを足す。
   ルールに無いコレクションはすべて拒否される。

   | コレクション | 読み取り | 書き込み |
   |---|---|---|
   | `markers/{id}` | 誰でも | 作成は本人。更新・論理削除は本人か管理者。物理削除は管理者 |
   | `admins/{uid}` | 本人か管理者 | 管理者 |
   | `blacklist/{uid}` | 本人か管理者 | 管理者 |
   | `rateLimits/{uid}` | 本人 | 本人（削除は不可） |

2. **時刻は Firestore の Timestamp で持ち、書き込み時は `serverTimestamp()` を使う。**
   ルールで `request.time` と一致するかを検査できるため。`MarkerData` の epoch ms への変換はアダプタが行う。
3. **マーカーの持ち主は `ownerUid`（Firebase の uid）で判定する。**
   `createdBy` は表示名として残し、権限の判定には使わない。`ownerUid`・`createdBy`・`createdAt` は作成後に変えられない。
4. **利用者単位のレートリミットは「印」で実現する。**
   マーカーを書くバッチで `rateLimits/{uid}` を `{ lastWriteAt: serverTimestamp(), target: <マーカー ID> }` に更新させ、
   マーカー側のルールは `getAfter()` で印が同じ書き込みのものかを確かめる。
   - 印の更新は直前から **6 秒以上**あいていないと拒否する（要件 1.3 の 10 回/分に相当）。
   - `target` が 1 つなので、1 回のバッチで作れるマーカーは 1 件に限られる。
   - 管理者の更新・削除は一括操作のため印を求めない。
5. **本人は論理削除まで。** 論理削除済みのマーカーを本人は戻せない。復元と物理削除は管理者だけ。
6. **ブラックリストに入った利用者は、管理者であっても書き込めない。**

## 検討した代替案

- **マーカーの文書に直前の書き込み時刻を持たせる**: 更新の間隔は制限できるが、
  新規作成の連打は文書ごとに別なので止められない。却下。
- **ユーザーのプロフィール文書に時刻を持たせる**: プロフィールは本人が他の項目も書き換えるため、
  ルールが複雑になる。専用のコレクションに分けた。
- **時刻を epoch ms の数値で持つ**: クライアントの時計を信じることになり、ルールで検査できない。却下。

## 結果

- 書き込み 1 回あたり、ルールの `exists()`・`getAfter()` で読み取りが 2〜3 回ぶん数えられる（無料枠の読み取りから引かれる）。
- アダプタ（T5）は、マーカーの作成・本人の更新を必ず `writeBatch` で印と一緒に書く必要がある。
  印の無い書き込みは拒否される。
- 最初の管理者は、コンソールか Admin SDK で `admins/{uid}` を手で作る（ルールでは誰も最初の 1 人を作れない）。

## 確かめ方

```text
npm --prefix project run test:rules
```

エミュレータ（JDK 11 以上が要る）で `tests/rules/` を実行し、0010 の「要件ごとの実装可否」のうち
ルールが担う ○ の行（1.1・3.x・5.x 管理者・1.3 利用者単位）と 5.x ブラックリストの書き込み拒否を検査する。
2026-09-24 の実行で 38 件中 38 件 OK（JDK 25 / firebase-tools 15.30.2）。
