# 0013. 同期より後の変更は、すべて updatedAt を進める書き込みで表す

- 状態: 採用
- 日付: 2026-09-24
- 関連: [0004](0004-静的JSONを一次ソースにする.md)、[0010](0010-書き込みと認証にFirebase無料プランを使う.md)、[0012](0012-Firestoreのデータ形とルールの方式.md)

## 背景

閲覧の土台は、GitHub Actions が毎晩作り直す `markers.json` と `requests.json` である。
それより後の変更は、Firestore の onSnapshot で「同期した時刻（`syncedAt`）より後の変更」だけを購読して埋める（要件 1.4）。

撮影リクエストの取り下げを、最初は**物理削除**で実装し、購読は**作成日時**で絞っていた。
その結果、同期より前に作られたリクエストを取り下げても、その取り下げは誰の購読にも届かなかった。
公開データには次の同期まで取り下げ済みのリクエストが残り、画面で「あなたのリクエスト」として出て、
もう一度取り下げようとするとルールに拒否された（2026-09-24、本番で発生）。

同期の回数を増やしても、古い姿が見える時間が短くなるだけで無くならない。
書き込みのたびに同期する仕組みは、Spark では Cloud Functions が使えず、ブラウザから Actions を起動するにはトークンを画面に持たせる必要があるので採れない。

## 決定

1. **同期より後の変更は、すべて `updatedAt` を `serverTimestamp()` に進める書き込みで表す。**
   差分の購読は、どのコレクションも `updatedAt > syncedAt` で絞る。
2. **利用者は物理削除しない。** 削除・取り下げは論理削除（マーカーは `deleted: true`、撮影リクエストは `withdrawn: true`）。
   ルールで本人の物理削除を拒否する。
3. **日次の同期は、論理削除済みの行を公開データに含めない。**
4. **管理者の物理削除は、同期とセットで行う。** 物理削除は購読に届かないので、削除したら `gh workflow run sync-firestore.yml` で公開データを作り直す。
5. 撮影リクエストの取り下げは、`withdrawn` と `updatedAt` だけを変え、同じバッチで熱量の印（`heatBudgets`）を減らす。
   取り下げ済みを再び取り下げて熱量を二重に戻すことは、ルールで拒否する。
   （2026-09-25 追記。ADR 0028）届いた動画の受け取りは、`answeredBy` を足した取り下げ。`updatedAt` も進むので購読に届く。

## 検討した代替案

- **同期を 1 時間ごとにする**: 古い姿が見える時間が短くなるだけ。却下（補助としては可）。
- **取り下げ済みを画面が見つけたら無視する**（「もう無ければ取り下げ済みとして扱う」）: 取り下げの失敗は防げるが、
  他の人の画面には次の同期まで古い集計が出続ける。症状への対処で原因が残る。却下。
- **購読を作成日時と更新日時の 2 本にする**: クエリが増えて読み取りの無料枠を使う。論理削除にすれば 1 本で済む。却下。

## 結果

- マーカーと撮影リクエストの作りがそろい、「同期より後の変更はすべて購読に届く」が成り立つ。
- 取り下げ済みのリクエストは Firestore に残る（誰がいつ取り下げたかの記録にもなる）。ストレージは無料枠内で問題にならない見込み。
- 管理者が物理削除したときだけ、同期の手動実行が要る。

## 確かめ方

`npm run test:rules` の「同期より前に作られたリクエストの取り下げも、購読で届く（ADR 0013 の回帰テスト）」と、
ルールの「本人でも物理削除は拒否」「取り下げ済みをもう一度取り下げて熱量を二重に戻すのは拒否」が通ること。
